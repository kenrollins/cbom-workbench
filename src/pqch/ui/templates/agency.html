Why an answer key

A scan of a real network says what it found; it cannot say what it missed. Here every cryptographic item is written down before any scan runs, so each run is scored against it — found, missed, or fooled.

{{ e.totals.present }} to findPresent and reachable: a key exchange a listener accepts, a certificate it serves, a key file in an image, a weak setting in a configuration file.
{{ e.totals.decoy }} decoysThings that look like findings and are not: a certificate left in an image that nothing serves, a weak setting in a comment or a file the software never loads. Reporting one is a false positive; a scanner that greps does.
{{ e.totals['out-of-reach'] }} out of reachReal, but invisible to any probe from this side: what the file drop offers when it connects out, and which keys partners present. Only passive capture beside them would show it. They stay in the score's denominator and are reported as known misses: the limit of a scan is part of the result.
{{ e.totals.supplied }} suppliedWhat no scan can discover — the mission each service carries, how long its data must stay secret, whether it is a high-value asset — typed in by the owner. The CBOM carries them labelled supplied, and they never count as coverage. They decide what comes first in the plan.

The roles and clients above are the agency's story; the workbench learns none of it from this page. What it knows comes from the evidence — the wire, the images, the code — and from the owner's facts. Certificates and keys are generated when the images are built, so the key names them by path and algorithm, never by fingerprint. The full list: agency/answer-key.yaml.
