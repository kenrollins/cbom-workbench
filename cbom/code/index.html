Inside the CBOM. The inventory itself — the mini-agency's or the lab's — opened up: drawn along its chain, what the document holds, one entry field by field with the evidence behind each field, the same record projected another way, and what changed since the last scan.

A Cryptography Bill of Materials is a CycloneDX document whose components are cryptographic assets — algorithms, certificates, keys, protocols — each with where it was found and what depends on it. This page opens the one this run produced: the whole document, then one entry, field by field, each traced to the ledger event it came from. It is also what a model is given. When the investigator traces a weakness to the line that causes it, or a change is drafted, the entry below is the context: the service, the listener, the file, the evidence. The model's answer is checked against it, and the change is proved on the wire.

This is the code layer's CBOM: candidate call sites in one pinned repository, found by a rule pack and judged by the call-site-read role, whose judgement is the entry's pqch:in-use. The mini-agency's CBOM.

What the standard settles, and what it leaves open

CycloneDX 1.6 (ECMA-424) defines the asset types and their fields: an algorithm's primitive and parameter set, a certificate's subject, issuer and validity, a key's type and size, a protocol's type; where each was found; and what depends on what. It does not say who owns an asset, which policy queue it is in, whether a file in an image is actually served, or what observation an entry rests on. Those go in properties under a namespace the producer chooses — here pqch:. What a federal CBOM must contain is not yet settled either: CISA and NIST publish the minimum elements by 2027-03-19.
