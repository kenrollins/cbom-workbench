# Changes to the specification

What changed in `interfaces.md`, and why. Newest last. A change made while an
interface is still a draft does not bump its major version.

| Date | Interface | Change | Why |
|---|---|---|---|
| 2026-10-03 | `pqch.event/1` | Added the event type `scan.completed` (actor `runner`), carrying one runner job's result; `finding.observed` names it in `inputs` | The measured scan time per endpoint, scan failures and timeouts, and the scanner digest had nowhere to live: a failed scan yields no findings, so without this event it would leave no trace. Additive |
| 2026-10-03 | `pqch.event/1` | Stated that each run has its own ledger file at `var/runs/<run-id>/ledger.jsonl` | `run.started` is "always `seq` 0 of a run" and `seq` starts at 0 per ledger, which already implies one file per run; the text said "one file" |
| 2026-10-03 | `pqch.scope/1` | Added an optional `image` to each endpoint: the scoped image serving that listener | The rule that marks a certificate in an image as not served needs to know which listeners that image serves. The compose file states it; the scope did not carry it. Additive |
| 2026-10-03 | `pqch.finding/1` | Stated the exact object hashed for `fingerprint`: `{"layer", "subject", "type", "role", "name"}` | `{layer, subject, asset.type, asset.role, asset.name}` left the key names open, and two implementations could hash different objects |
| 2026-10-03 | `pqch.finding/1` | The example's X25519 key-exchange group now has `asset.type` `algorithm`, not `protocol` | A key-exchange group is an algorithm in CycloneDX (`primitive` `key-agree`); the protocol is TLS. The example contradicted the asset types table |
| 2026-10-03 | `pqch.event/1` | Verification now also requires: event 0 is `run.started`; ids unique; `inputs` name earlier events; `ts` never goes backwards; the actor kind fits the type; a finding's `fingerprint` matches the finding; approval and apply events name a change id. Stated what the chain alone cannot detect | M0 review, F-27: a ledger rewritten with its hashes recomputed passed with a verdict issued by a human, dangling inputs and wrong fingerprints. Tightens validity while the interface is a draft |
| 2026-10-03 | `pqch.scope/1` | `host`, `sni` and `protocol` restricted to characters that cannot be read as a scanner option. The runner reads the scope once at start; the UI service cannot write it | M0 review, F-26 and F-29: the UI service could rewrite the scope the runner enforced, and a scope value beginning with `-` reached the scanner's command line |
| 2026-10-03 | `pqch.scope/1` | Stated that an endpoint's `host` is a single address | ADR-0003 speaks of "hosts or address ranges"; the schema never carried a range. Said plainly before the schema is frozen (M0 review) |
| 2026-10-03 | `pqch.finding/1` | A file subject's `image` is the repository only; the scanned image's digest moves to `source.subject_digest`. Added `asset.identity` (`spki-sha256:` or `openssh-sha256:`), and the fingerprint object gains `identity`. Changes the meaning of `fingerprint`; done while the interface is a draft, so no major bump. Ledgers written before it fail fingerprint verification | M0 review F-37: the fingerprint could not tell one RSA key from another, so a replaced certificate or regenerated host key was "the same observation"; and every rebuild of an image changed every host fingerprint, so a re-scan would see a new estate |
| 2026-10-03 | `pqch.checkpoint/1` | Stated who signs (a signer service that verifies the chain itself and keeps its own record of what it signed), that the checkpoint before `run.closed` covers every event before it, how a recorded checkpoint is checked against the ledger, and that the public key is checked against the signer's, not only `ledger.pub`. The `checkpoint.signed` payload may carry `signing_ms` and `hardware`. `key_id` is over DER SubjectPublicKeyInfo | Spike S4 and M0 review F-28: without a record outside the ledger, a checkpoint cannot show that events after it were cut; and `ledger.pub` sits beside the ledger, so it can be replaced along with it. Additive |
| 2026-10-03 | `pqch.event/1` | `scan.completed` for a wire scan carries `binding`: the container at the address, its image digest, and whether it stayed the same through the scan. A new rule, `binding/scope/1`, records per listener whether that image is the one the scope names; wire and host evidence for an unbound listener is never joined | M0 review F-31: with the estate running other images than the scope named, the workbench linked nothing, judged the served certificates unused and scored below both baselines, without a word. Additive |
| 2026-10-03 | `pqch.event/1` | Added "Who writes the ledger": one writer, the harness process; what the runner checks before it applies; how an approval records who and how they were authenticated; and where that trust stops. New event types `policy.changed` (human) and `service.recreated` (runner). `change.applied` names the containers before and after | M0 review F-38: events said `runner` and `human` while the UI process wrote them all, and nothing bound an approval to a person. Decided before the approval path was written. Additive |
| 2026-10-03 | `pqch.verifier/1` | The example's tools corrected to what is built: the paired probes are OpenSSL `s_client` handshakes offering only the named groups, the witness is testssl.sh. Each probe records its container, image digest and stability; the verdict adds `meets_intent`, `reasons`, `hardware`, and, when repeated or retargeted, `repeats` and `target_override`. The check adds `policy_intent`, and a policy of `none` is checked as `require` with the classical group accepted | M0A: testssl.sh cannot offer only one group, so it cannot be the negative probe a client that would downgrade represents; it can enumerate what a listener accepts, which is what a witness of a different kind needs. Additive |
| 2026-10-03 | `pqch.event/1` | Nothing may follow `run.closed`: the ledger refuses the append, and verification fails a ledger that has one | M0A: a check was appended to a closed run, and nothing stopped it |
| 2026-10-03 | `pqch.verifier/1` | `must_refuse` is every group of the other kind, not the configured ones. A witness that finds any accepted group outside `must_accept` caps the status at `enabled-not-enforced`; the verdict gains `also_accepts` | M0A review F-44: a listener offering the hybrid group and secp384r1 was given `enforced`, because the negative probe offered only the policy's two classical groups and the witness's list was not read |
| 2026-10-03 | `pqch.event/1` | "Who writes the ledger": the page believes the sign-on header only from the front door's address; the runner writes only configuration of the rendered shape and restores the old file if the service does not come up; verdicts and timestamps are named as the harness's own | M0A review F-45, F-46: a request from a neighbour on the same VLAN with a typed-in header was recorded as a signed-on approval and applied; a forged proposal put an arbitrary directive into the service's configuration |
| 2026-10-04 | `pqch.checkpoint/1` | The signer's own UTC time, `signed_at`, is in the checkpoint and is the fourth line of the signed message. It brackets the ledger's timestamps within 2000 ms; the signer refuses, and verification fails, a ledger outside the bracket. Checkpoints from before have no `signed_at`, verify over the old message, and are reported as legacy. The signer refuses a ledger whose `run.started` names another run. Time-to-change is also reported from signer times | M0A review F-47: both time-to-change intervals rested on the harness's clock, and a checkpoint signed order and content but not time. Changes the signed message; the interface is still a draft |
| 2026-10-04 | `pqch.event/1` | `run.started` carries the run's id. The runner logs every job it runs; a verdict's probes carry `job_id`, and each is checked against that log | M0A review F-47 and F-53: a ledger was a run's only by its directory, and nothing tied a verdict's probes to jobs the runner ran, so older raw output could be quoted in a new verdict. Additive |
| 2026-10-04 | `pqch.event/1` | The runner refuses a `change.proposed` whose `diff` is not the diff between its `rollback` and its new content, or whose `rollback` is not the configuration now deployed | M0A review F-46: an approver reads the diff, and nothing checked it against what would be applied |
| 2026-10-04 | `pqch.verifier/1` | A probe is judged by the group the server chose: a server key share in an offered group is acceptance even if the client then aborts | Spike S2: RabbitMQ accepted a Brainpool curve over TLS 1.2 and OpenSSL aborted afterwards on the certificate's curve; the probe parser called that an error. The status table is unchanged |
| 2026-10-05 | `pqch.checkpoint/1` | A checkpoint is written immediately before `policy.changed` and before each approval, so each is written between two signatures; time-to-change on the signer's clock is defined as an upper bound, from the last signature before the event to the first over the verdict. The signer refuses a `run.started` that names no run, signs only forward, and never issues a `signed_at` earlier than its last for the run. Clients mount its socket read-only. The object and the signed message are unchanged | M0B review F-54: before a run's first checkpoint a timestamp had no lower bound, so a policy event could be backdated by an hour or held and restamped, and both clocks agreed; a ledger copied under a new id with the run name cut out was signed; a signer clock stepping back 1.9 s produced a checkpoint that failed verification; the UI process could put its own socket in the signer's place |
| 2026-10-05 | `pqch.verifier/1` | Added "Checking a verdict against the runner's record": the job must be the one the check prescribes, started after the runner's own apply and against the container it made, and the runner's raw output must give the probe's result and the verdict's status. A change is shown as verified, with a time-to-change, only when borne out. The verdict object is unchanged | M0B review F-55: the page passed a forged `enforced` whose negative probe was a genuine job run with one hand-picked group, and one whose probes were quoted from an earlier run's jobs; it compared hash, times and container with the log and nothing else |
| 2026-10-05 | `pqch.event/1` | "Who writes the ledger": the runner restores the previous file when the service does not listen, logs the attempt as `apply-failed`, recreates with every Compose file the estate was started with, and accepts only printable ASCII in a comment line. `scan.completed` carries `hardware` | M0B review F-56, F-57, F-61, F-64: a right-shaped file nginx could not load was left deployed with the portal down and logged as an apply; a recreate on a bundle-started estate would use the base file's image; a carriage return in a comment showed an approver a line the service does not read; an emulated run's scan times were shown under the serving machine's label. Additive |
| 2026-10-09 | `pqch.scope/1` | Added optional `captures` (interface, host, VLANs, mirror) for an `external` estate, and optional `vlan` on an endpoint; a capture run is opened with the harness's own scope hash and `kind: capture` | The owner's lab is the first external estate (ADR-0003 as amended): passive capture from a switch mirror comes before any active check, and the scope must say where the sensor listens and under whose authorization |
| 2026-10-09 | `pqch.finding/1` | Added the subject kind `client` (`host`, `protocol`, optional `vlan`), and optional `vlan` on an endpoint subject | Passive capture sees what a client offers in its handshakes; a client is not a listener and has no port of its own, and the VLAN a mirror preserves is where a device sits |
| 2026-10-12 | `pqch.inference/1` | A tier may carry `reasoning` (model, timeout_s, request fields) for the same engine with reasoning on; a `roles` section binds each role to a tier and a reasoning flag; `complete` takes `reasoning`, `complete_role` takes a role; a completion and its actor record reasoning, role, `finish_reason` and `served_by` (the upstream named in a response header, `served_by_header`). Frozen at this shape | Spike S3: call-site reads and classification reach their floor only with the small engine's reasoning on, and the spike had to fake that with a second config file. Which role runs where is a measurement, so it is data in the file, never a default in code |
| 2026-10-19 | runner profiles, `pqch.finding/1` | New wire profile `tls-starttls-postgres` (testssl.sh speaking PostgreSQL's SSLRequest upgrade), bound to scope listeners whose `protocol` is `postgres`; `tls-targeted` refuses them. A wire finding's `subject.protocol` is the listener's protocol as the scope names it, so a finding behind an upgrade says `postgres`, not `tls`; the certificate and in-use rules treat `tls` and `postgres` listeners alike. Additive | M0B review F-62, M1: the records database is the estate's one listener that accepts RSA key transport, and a scan that does not speak the upgrade would have inventoried it as nothing at all |
| 2026-10-19 | runner profiles, `pqch.finding/1` | New host profile `image-files`: the harness's own reader (`pqch image-files`, tool `pqch-image-files`), run from the runner's image with no network over the archive theia receives, one job per scoped image beside theia's. It reads PEM and DER certificates (ML-DSA included), private and public keys (OpenSSH included), DH parameters and PKCS#12 keystores (passwords tried: none, empty, `changeit`, and which one opened it is recorded); a certificate finding carries `is_ca` (basicConstraints CA with keyUsage keyCertSign) and `basic_constraints_ca`; every entry carries `referenced_by`, the configuration-like text files that name the file. In neither baseline. The in-use rule leaves a CA's certificate file alone | M1: theia drops an ML-DSA certificate, cannot open a keystore, misses DSA and Ed25519 keys, and the not-served rule marked the internal CA's certificate not in use because no listener serves a CA's certificate |
| 2026-10-20 | `pqch.scope/1`, `pqch.event/1` | An endpoint may carry `service`, the compose service that serves it, written by the generator. `link.asserted` `from`/`to` may be subject objects (endpoint, image, service, fact) as well as finding ids; a supplied link has a human actor, `status: supplied`, a `source` and the owner's file in `evidence`. Two new rule assessments: `verifier/class/1` per finding class and `conflict/resolve/1` per judged finding, with the conflict vocabulary spike S3 labelled; a model's explanation is its own assessment, `used_by_rules: false`. The CBOM projection gains `application` and `container` components and the chain's dependencies, and `pqch:verifiable-by` and `pqch:conflict` on assets. Additive | M1, the Structured rung: the chain listener → certificate → service → mission function → data lifetime, each link with evidence and supplied links labelled; ADR-0001 decision 5 (a finding class with no verifier is recorded as such and counted in the receipts); S3's R4 rebuilt as a rule after no arm reached its floor |
| 2026-10-20 | `pqch.event/1` | New event type `trace.completed` (actor `model`): the investigator's loop over a service's configuration files under step and token budgets, recorded with the engine, the settings, every step and the measured time; written in a run of kind `investigate` that names the scan run and finding it traces. Additive | M1: the trace from a wire finding to its line is a model's claim and is recorded as one, beside the evidence and never in place of it |
| 2026-10-20 | `pqch.event/1`, `pqch.finding/1` | The Managed rung's rule assessments (vulnerability, pack scope, priority, queue, TLS 1.3, supplier and validated-module blockers), each naming its pack, the PDF's hash and the section quoted; a policy pack refuses to load when a quote is not in its source text. A wire finding of type `protocol` per TLS version a listener accepted a suite with. New event type `config.observed`; `change.observed` gains the kinds watch mode writes. Additive | M2: the queues and blockers are rules over the memo's own words and two dated snapshots, and watch mode needs a record of what each scan saw to say what changed |
| 2026-10-21 | `pqch.scope/1`, `pqch.event/1`, `pqch.verifier/1`, runner | A scope may list `twins`; the runner starts a copy of a service there to rehearse a proposal (`/rehearse`, `/rehearse/end`) and probes it on the twin network. `change.proposed` from a model carries `drafted`; `rehearsal.completed` carries the copy's verdict; the runner refuses to apply a model's proposal without a rehearsal of that file that met its intent. A `require` check carries `refuse_tls12` and prescribes a legacy TLS 1.2 probe, which must be refused; probe and witness profiles for PostgreSQL's upgrade. The runner writes a policy file only in the shape the estate's compose file declares for the service's software. Additive | M3: a change drafted by a model for software with no renderer, proved on a copy before approval; and a verifier that could call a PostgreSQL listener enforced while it still accepted RSA key transport over TLS 1.2 |

| 2026-10-21 | `pqch.event/1` | Added the event type `package.issued` (actor `rule`, `package/supplier/1`) in a run of kind `package` over a scan run: a change package for an item blocked on its supplier, with the capability evidence, the upgrade path the estate already holds, the CBOM entries covered and the check that will count once replaced. Cross-run references (the blocker and queue events) are named in the payload by run and event id, since `inputs` names only events of the same ledger | M3: an item no configuration change can move had no record beyond the blocker, and the Mitigation part of NIST CSWP 39-upd1 Fig. 3 had nothing to show. Additive |
| 2026-10-21 | `pqch.event/1` | Added the event type `matrix.completed` (actor `verifier`): kinds of client probed against the listener as deployed and a twin with the proposed file, with each one's effect. The ledger's actor table now names `matrix.completed` (verifier) and `package.issued` (rule) | M3: a `require` change verified `enforced` says it landed, not whom it refuses; the approver needs that before approving. Additive |
| 2026-10-21 | `pqch.event/1` | Added runs of kind `import` and the event type `import.completed` (actor `scanner`): another tool's CycloneDX CBOM brought in as evidence. Its entries are `finding.observed` events with `source.tool` the tool, `source.image_digest` the imported document's hash and `source.profile` `import:<tool>`; an entry is placed only where the workbench can find it again (a scoped listener, a file in a named image, a call site in a pinned repository), and the rest are listed by name in `import.completed` with the documents, counts and, when a key is given, the score | Bring your own scanner: federal agencies use commercial discovery tools; scoring their output against the planted estate on the workbench's own terms needs no integration. Additive |
